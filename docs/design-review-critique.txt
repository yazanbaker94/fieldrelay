Verdict

The document is strategically excellent but not yet a complete design brief.

My rating:

Area	Rating	Why
Product thinking	9/10	Strong workflow, failure handling, auditability and demo narrative
Fit for WiQ role	9/10	Directly demonstrates end-to-end ownership, React/React Native, Node, PostgreSQL and AWS
Engineering scope	8/10	Credible architecture, but too large for a portfolio prototype
UX specification	7/10	Covers screens and states well, but several workflow decisions remain unresolved
Visual direction	5/10	“Industrial, modern, trustworthy” is not specific enough to prevent generic SaaS output
Recruiter usability	7/10	Guided demo is smart, but the full experience still asks too much of a reviewer

The central idea is very strong. WiQ explicitly wants somebody who can receive an ambiguous business problem, learn the rules, design the whole flow, account for edge cases, and own it through release. FieldRelay demonstrates exactly that. WiQ’s current role description strongly validates the project direction.

The biggest risk is not that FieldRelay looks bad. It is that it becomes a massive, polished, generic enterprise dashboard and never communicates your actual product judgment.

What the brief gets right
Failure-first engineering is the strongest differentiator. Offline work, duplicate submissions, conflicting quantities, failed integrations and reconstruction through audit history all match the kinds of edge cases WiQ specifically says developers must discover themselves.
The end-to-end shipment story is far stronger than a collection of disconnected portfolio screens.
The guided demo is essential. A reviewer should understand the product without installing an APK.
Synthetic data, independent branding and disclaimers are handled responsibly.
The architecture is aligned with the position without pretending to reproduce WiQ.
The Android app is treated as a real product rather than a responsive dashboard.
The document correctly emphasizes templates, auto-filled fields and fast field entry. WiQ says its real field workflow works offline and that many manifests can be completed in under a minute. WiQ energy workflow
What must be fixed before design starts
1. The scope needs three priority levels

The current brief asks for roughly 30 designed screens, four deployable applications, a real-time event system, SQS, DLQ, OData, signatures, QR handoffs, audit history, observability, documentation and two walkthrough videos.

That is closer to a funded MVP than a portfolio demo.

2. The state model is visually and logically overloaded

The 19 listed states should not be one giant status system. They belong to four parallel dimensions:

Dimension	Examples
Shipment lifecycle	Draft, offered, accepted, in transit, received, completed
Device synchronization	Saved on device, queued, syncing, synced, needs review
Business exception	None, discrepancy open, resolved
External delivery	Not started, pending, retrying, failed, DLQ, delivered

A shipment should be able to display:

Received · Saved on device · Discrepancy open · Export not started

Those are not interchangeable colored badges. On list screens, show the shipment stage plus only the highest-priority secondary condition. Show all dimensions on the detail screen.

3. Several business rules remain undefined

The agent needs answers to these before designing interactions:

Does a discrepancy prevent Completed?
Does “accepted final quantity” become a new derived value, or overwrite the receiver quantity? It should be a new value; reported values must remain immutable.
What exact demo threshold triggers a discrepancy?
Why is the offered-to-pickup difference of 20 L accepted while the pickup-to-receipt difference of 240 L is flagged?
What event changes Picked up into In transit?
Can a driver handoff opened from a web link work offline? Normally it cannot unless the token and shipment were preloaded.
What happens when the server accepts an operation but the device loses connectivity before receiving the response?

My recommended demo rule:

Flag a discrepancy when the pickup-to-receipt difference exceeds both 1% and 100 L.

For the sample shipment:

Offered → pickup: −20 L / −0.24%
Pickup → received: −240 L / −2.93%
Result: discrepancy open
Shipment remains Received until resolved
Resolution records a separate Accepted final quantity
Only then can it become Completed

If the response disappears after the server processed a mobile operation, the UI should show Checking sync result, retry with the same idempotency key, and then recover the original result. It should not briefly tell the user the save failed.

4. The mobile diagnostics are too technical

A driver should not see UUIDs, operation IDs and attempt counts as primary information.

The main sync row should say:

Shipment FR-2026-0842
Receipt saved on this device
Waiting for connection

Then an expandable Technical details area can contain:

Local operation ID
Attempt count
Last error
Diagnostic ID

Fulcrum uses an unsynced-record count and automatic synchronization while keeping deeper sync mechanics secondary. ArcGIS similarly exposes troubleshooting logs when sync actually fails. Fulcrum mobile sync, ArcGIS Field Maps sync

What I would tell the other agent

Do not let him begin with all 30 screens. Send this instruction:

Keep the product and engineering brief as the source of truth, but establish a specific “instrumented chain of custody” design language before producing screens. Use IBM Plex Sans, signal blue rather than WiQ green, near-white operational surfaces, compact borders, restrained radii, and a connected-node relay motif.

First design the landing hero, web exception workbench, integration-delivery detail, mobile home offline state, mobile review/offline-save success, sync status and receiver discrepancy. These screens must establish the complete system. Derive the remaining list, audit, settings and system screens from those components.

Separate shipment stage, sync state, exception state and export state rather than treating all statuses as one badge system. Keep technical operation IDs behind expandable details on mobile.

The public site must present a portfolio case study, not a fictional startup marketing page. The browser-based guided demo must show the entire value without requiring APK installation. Use real product data and event transitions as the visual signature; avoid gradients, oversized rounded cards, stock industrial photography and generic dashboard charts.

So: keep the document, but revise the unresolved workflow rules, reduce the primary screen set, and give the agent this much stronger art direction before he starts.
